каталога фильмов по TMDB — веб-админка с загрузкой видео и HLS-стримингом.

## Архитектурные решения (зафиксированы, не пересматривать без явного повода)

| Вопрос | Решение | Почему |
|---|---|---|
| Транскодирование | Фоновая очередь: Celery или RQ + Redis как брокер | Синхронно/BackgroundTasks не переживёт долгую обработку 10ГБ файла и не масштабируется на несколько воркеров |
| Загрузка файла | Chunked/resumable upload | Единственный реалистичный способ надёжно принять файл в единицы–десятки ГБ через HTTP |
| Хранилище видео/HLS | MinIO (S3-совместимое, локально в Docker) | Ближе к тому, как это делают в проде (объектное хранилище, не локальный диск) |
| Frontend | Отдельный SPA на Angular 22 поверх API (пишет Claude по просьбе пользователя) | У меня уже есть сильный frontend-опыт — делаю по-взрослому, с разделением backend/frontend как в реальных проектах; фокус обучения — backend |
| Пользователи | Полноценная таблица users, регистрация, роли (admin/viewer) | Не "один admin из .env" — хочу практику именно с авторизацией как доменной задачей |
| БД | PostgreSQL + SQLAlchemy (ORM) + Alembic (миграции) | Из roadmap.html, плюс миграции — то, что реально используется в проде |
| Веб-сервер | nginx перед FastAPI, отдаёт HLS-сегменты и, возможно, статику SPA | Учебная цель — понять зачем нужен reverse proxy и как раздавать медиа с range-requests |
| Python deps | uv (не poetry, не голый pip+venv) | Быстрее, единый инструмент для venv+pip+версий Python, де-факто стандарт в новых проектах |
| Форматирование/линт | Только ruff (не black+ruff отдельно) | У ruff свой форматтер, совместимый с black; один инструмент вместо двух, от той же команды (Astral), что и uv |

**Шаги/находки:**

- При написании тестов всплыл баг в фикстуре `unique_email` (conftest.py):

  был выпущен `refresh_token` — фикстура не чистила связанные токены перед

- Найдено (не починено, только смягчён тест): access-токен не гарантированно

  считается с точностью до секунды, а payload больше ничего не меняет.
  Обсудить отдельно, стоит ли добавлять `iat`/`jti` в payload.

### Этап 2 — Простой CRUD для видео (ещё без файлов) (закрыт)

Цель: научиться доменной модели и связке с пользователем, прежде чем
усложнять загрузкой файлов.

- [x] Модель `Video` (метаданные: название, описание, статус обработки,
      owner_id) — сделано на Этапе 3 попутно, есть `create`
- [x] `GET /videos` (список) и `GET /videos/{id}` (одно видео) — сознательно
      **публичные, без авторизации**, без фильтра по владельцу: видит любой,
      залогинен или нет. `GET /videos/{id}` на несуществующий id — 404
      (сервисная `video_by_id` кидает `VideoNotFoundError`, роут ловит и
      возвращает 404)
- [x] `DELETE /videos/{id}` — требует авторизации (`Depends(get_current_user)`),
      только владелец может удалить своё видео (404 — видео не найдено, 403 —
      чужое видео). Удаление — оркестрация в `video_service.delete_video`:
      чанки на диске (если остались) → объект в MinIO (если файл был
      загружен) → запись `VideoUpload` → сама `Video`
- [x] Слои: роут → сервис → репозиторий → БД. `video_repository.py` — только
      SQL/ORM операции, бизнес-логика (проверка владения, оркестрация
      удаления файлов) — в `video_service.py`
- [x] Тесты (`backend/tests/test_video_crud.py`, 11 тестов, написаны Claude):
      list публичен и включает чужие видео, list без токена, get своего
      видео, get без токена, get несуществующего (404), delete успешный
      (включая проверку что видео пропадает из get после), delete чистит
      файл в MinIO если он был загружен, delete не трогает MinIO если
      upload не начинался, delete без токена (401), delete чужого видео
      (403), delete несуществующего (404). Общие фикстуры/хелперы
      (`_clean_videos`, `_clean_upload_tmp_dir`, `register_and_login`,
      `create_video`) вынесены в `conftest.py`, переиспользуются также
      `test_video_upload.py`.

**Шаги/находки:**
- Осознанное архитектурное решение (обсуждено с пользователем): видимость
  видео **не завязана на владельца** — `list`/`get` полностью публичные
  (как каталог), без авторизации и без ownership-фильтра. Роли admin/viewer
  здесь не участвуют. `owner_id`-проверка есть только там, где она нужна по
  смыслу — при `delete` (и при upload-операциях, сделанных на Этапе 3).
- При первой реализации `delete_video_by_id` в репозитории было несколько
  последовательных багов, найденных и починенных по ходу ревью: (1)
  `session.delete(select(...))` — `session.delete()` ожидает ORM-объект, а
  не `Select`; (2) отсутствие `await` на асинхронной функции удаления
  файлов — тело тихо не выполнялось; (3) двойной `session.delete(video)` +
  `commit()`; (4) `session.get(VideoUpload, video_id)` искал по
  первичному ключу вместо `video_id`; (5) циклический импорт
  `video_repository → video_service → video_repository`, когда
  файлово-сетевая логика удаления временно жила в репозитории. Исправлено
  разделением по слоям: `video_repository.delete_video` — чистое удаление
  ORM-объектов из БД, `video_service.delete_video` — оркестрация
  (owner-check, удаление файлов, вызов репозитория),
  `video_service._delete_video_upload_files` — приватный хелпер сервиса.
- Найден и починен баг **порядка удаления при одном `commit()`**:
  `session.delete(video_upload)` и `session.delete(video)` перед общим
  `commit()` не гарантируют, что DELETE для `video_upload` уйдёт в базу
  раньше DELETE для `video` — SQLAlchemy сам решает порядок отправки, и в
  тесте `test_delete_video_removes_uploaded_file_from_storage` он оказался
  обратным, что упало с `ForeignKeyViolationError` (тот самый отложенный на
  Этапе 3 баг с FK без `ON DELETE CASCADE`, теперь материализовавшийся не в
  тестовой фикстуре, а в реальном бизнес-сценарии). Починено пользователем:
  `await session.flush()` сразу после `session.delete(video_upload)`,
  форсируя реальный DELETE в базе до того, как `video` помечается на
  удаление. `ON DELETE CASCADE` в миграции остаётся альтернативой на
  будущее, если такое ручное упорядочивание станет неудобным при появлении
  новых таблиц, ссылающихся на `videos` (например, HLS-сегменты на
  Этапе 4) — отложено, не переделано сейчас.
- Ранее найденный баг с `unique_email` (Этап 1/3, FK без CASCADE) остаётся
  неисправленным в самой фикстуре — тесты по-прежнему чистят `videos`/
  `video_uploads` явно в `conftest.py` перед тем, как `unique_email` удаляет
  пользователя.

### Этап 3 — Загрузка большого файла (chunked upload) (закрыт)

Цель: научиться принимать файл в единицы ГБ по частям.

- [x] Модель `Video` + роут `create` (метаданные без файла)
- [x] Модель `VideoUpload` (миграция `create_video_uploads_table`), роут
      `POST /videos/{id}/upload` — регистрирует начало загрузки
      (`total_size`, `storage_path`), переводит `Video.status` в `UPLOADING`
- [x] Протокол chunked upload: клиент режет файл на чанки фиксированного
      размера (`settings.upload_chunk_size_bytes`, кроме последнего чанка),
      шлёт их по одному через `PUT /videos/{id}/upload/chunks/{n}`; сервер
      складывает каждый чанк во временный файл `chunk_{n:06d}` в
      `upload_tmp_dir/{video_id}`
- [x] Хранение чанков и финальная сборка: `POST /videos/{id}/upload/complete`
      проверяет непрерывность номеров чанков и суммарный размер, склеивает
      их в `assembled.mp4`
- [x] Загрузка собранного файла в MinIO (`storage.py`, boto3 `s3_client`),
      статус `Video` → `UPLOADED`, временная папка чанков удаляется
- [x] Ручная проверка полного пути (`backend/scripts/test_upload.py`):
      логин → create → start upload → чанки → complete → файл в бакете
- [x] Тесты (`backend/tests/test_video_upload.py`, 8 тестов, написаны
      Claude): полный happy path, повторная отправка того же чанка
      (идемпотентность), complete с недостающим чанком, chunk без
      предварительного start, повторный start, чанк/complete для чужого
      видео, чанк для несуществующего видео, ошибка загрузки в S3 (502).
      `s3_client.upload_file` замокан — реальный MinIO для юнит-тестов не
      поднимаем, это будет частью интеграционных тестов на Этапе 6.

**Шаги/находки:**
- При написании тестов всплыл баг: роут `upload_complete` не перехватывал
  исключения `ChunksMissingError`/`ChunksSizeMismatchError` из
  `video_service.py` — при потерянном чанке или несовпадении размера клиент
  получал необработанный 500 вместо осмысленной ошибки. Согласовано с
  пользователем и починено: обе ошибки теперь возвращают 409 (as
  `UploadAlreadyStartedError`, консистентно с остальным роутом).
- Найдено, но **не починено** (отложено по решению пользователя): фикстура
  `unique_email` в `conftest.py` не чистит `videos`/`video_uploads` перед
  удалением пользователя — FK `videos.owner_id`/`video_uploads.video_id` без
  `ON DELETE CASCADE`. Тот же класс бага, что был с `refresh_token` на
  Этапе 1. Тесты на upload сейчас чистят `videos`/`video_uploads` сами через
  отдельную фикстуру в `test_video_upload.py`, не трогая общую `unique_email`.
  Стоит обсудить отдельно (CASCADE в миграции vs явная чистка в фикстуре) —
  особенно актуально станет на Этапе 2, когда появится `DELETE /videos/{id}`.

### Этап 4 — Транскодирование в HLS через очередь (закрыт)

Цель: собранный файл асинхронно превращается в HLS через ffmpeg.

- [x] Установка/использование ffmpeg из Python-кода (ffmpeg 9.0.2 через
      `winget install Gyan.FFmpeg`, вызов через `subprocess.run`)
- [x] Redis + RQ: воркер, очередь `video_processing` (`backend/queue.py`),
      `REDIS_URL` в `config.py`
- [x] Задача `transcode_video` (`backend/tasks.py`): MinIO → ffmpeg →
      сегменты .ts + .m3u8 → обратно в MinIO под `videos/{id}/hls/`
- [x] Обновление статуса `Video`: `processing` в начале, `ready` при успехе,
      `failed` + повторный raise при любой ошибке
- [x] Автозапуск: `enqueue(transcode_video, video.id)` в конце
      `upload_video_complete`, после `commit()`
- [x] Проверка `returncode` ffmpeg: при ненулевом коде бросается
      `TranscodeError(stderr)`, его ловит общий `except` и ставит `FAILED`.
      До этого при падении ffmpeg видео получало `READY`.
- [x] Adaptive bitrate: 1080p/720p/480p + `master.m3u8`. Качества описаны
      данными в `RENDITIONS`, команда собирается в `_build_ffmpeg_command`.
      `scale=-2:<height>` сохраняет пропорции, `-maxrate`/`-bufsize`
      ограничивают битрейт, `-force_key_frames` выравнивает границы сегментов
      между качествами (нужно, чтобы плеер мог переключаться)
- [x] Тесты (написаны Claude, 46 passed). `backend/tests/test_transcode.py`,
      5 тестов: успех (статусы `processing → ready` по порядку, скачан
      нужный `original.mp4`, в MinIO загружены `master.m3u8` и файлы всех
      качеств с правильными ключами), падение ffmpeg (`TranscodeError`,
      `failed`, ничего не загружено), падение скачивания (`failed`, ffmpeg
      не запускался), падение загрузки HLS (`failed`), сборка ffmpeg-команды.
      ffmpeg и `s3_client` замоканы; фейковый ffmpeg создаёт файлы в
      `hls_dir`, чтобы проверить цикл загрузки. В `test_video_upload.py`
      добавлены проверки: `enqueue` вызывается после успешного `complete` и
      не вызывается при недостающем чанке или ошибке S3. Ручной прогон с
      настоящим ffmpeg сделан (видео 79 и ABR); автоматический
      интеграционный тест — на Этапе 6.

**Шаги/находки:**
- Выбран RQ, а не Celery: Redis уже поднят, задача одна, Celery добавил бы
  конфигурацию без учебной пользы на этом этапе.
- Принятые решения: транскодирование запускается автоматически после
  upload/complete (не отдельным роутом); формат — adaptive bitrate; при
  ошибке видео просто помечается `FAILED`, без автоматического retry.
- На Windows обычный RQ `Worker` падает с `AttributeError: os.fork`, потому
  что в Windows нет `fork()`. Локально воркер запускается с
  `--worker-class rq.worker.SimpleWorker` (задачи выполняются в том же
  процессе, без изоляции). В Docker на Этапе 6 (Linux) можно вернуть обычный
  `Worker`.
- RQ вызывает задачи синхронно, а репозитории async. Решение:
  синхронная обёртка `transcode_video` вызывает `asyncio.run(...)` у async
  `_transcode_video_async`. Сессия БД берётся напрямую из
  `async_session_factory()`, потому что `Depends(get_db)` в воркере нет.
  Блокирующие `boto3` и `subprocess.run` обёрнуты в `asyncio.to_thread`.
- Баг при написании: код скачивания и ffmpeg стоял с отступом *снаружи*
  блока `with tempfile.TemporaryDirectory()`, то есть работал уже с
  удалённой временной папкой. Исправлено переносом всего кода внутрь блока.
- Ручная проверка через RQ worker прошла (видео 79): `complete` → 200 сразу,
  воркер выполнил задачу за ~6с, HLS-файлы появились в MinIO.
- При ручных экспериментах на синтетическом `testsrc` при ABR битрейты
  получились немонотонными (480p > 720p) — особенность VBR на простом
  контенте. Решено добавлением `-maxrate`/`-bufsize` в ABR-команду.
- Известные ограничения ABR, отложены: (1) апскейл — исходник ниже 1080p
  всё равно получает растянутый 1080p, лечится через `ffprobe` и фильтрацию
  `RENDITIONS`; (2) видео без аудиодорожки падает на `-map 0:a` и получает
  `FAILED`.
- На Этап 5: `upload_file` сохраняет HLS-файлы с типом
  `binary/octet-stream`. Для Safari нужны `application/vnd.apple.mpegurl`
  (`.m3u8`) и `video/mp2t` (`.ts`) через `ExtraArgs={"ContentType": ...}`.
- После добавления `enqueue` тесты Этапа 3 и CRUD-тест удаления, доходящие
  до `complete`, начали писать в настоящий Redis. Добавлена autouse-фикстура
  `mock_enqueue` в `conftest.py`, которая подменяет `video_queue` во всех
  тестах.
- Отложено на Этап 6: `StarletteDeprecationWarning` от импорта
  `fastapi.testclient` в одном из старых тестов; лечится переводом теста на
  `AsyncClient` + `ASGITransport`.

### Этап 5 — Раздача HLS и плеер

Цель: посмотреть загруженное видео в браузере через HLS.

- nginx: конфиг для раздачи сегментов (или проксирования к MinIO), range
  requests, CORS если нужно
- SPA: страница логина, страница загрузки (с прогрессом), список видео,
  плеер на hls.js
- Ручная проверка полного пути: логин → загрузка mp4 → дождаться обработки →
  посмотреть в плеере

**Принятые решения:**
- Доступ к HLS: nginx проксирует `/media/` → MinIO (бакет `videos`).
  Префикс `videos/*/hls/*` открыт на анонимное чтение через bucket policy,
  `original.mp4` остаётся приватным. Это согласуется с публичными
  `GET /videos`. Presigned URL отвергнут: в `master.m3u8` лежат
  относительные пути к вариантам и сегментам, а подпись действует на один
  объект.
- Ссылка на плейлист: в `Video` хранится **ключ объекта** в хранилище (не
  полный URL). API отдаёт вычисляемое поле `playback_url`
  (`/media/<ключ>`), когда статус `ready`, и `null` в остальных статусах.
  Хост и префикс раздачи зависят от окружения, поэтому в БД их не кладём.
- Хвост Этапа 4 (Content-Type для `.m3u8`/`.ts`) осознанно пропущен:
  hls.js работает и без него, страдает только нативный HLS в Safari.
- Где живёт nginx: в Docker, в `docker-compose.yml`, порт `8080`. Один origin
  для браузера: `/` → `ng serve` на хосте (`host.docker.internal:4200`),
  `/api/` → FastAPI на хосте (`host.docker.internal:8000`, префикс `/api`
  срезается), `/media/` → `minio:9000/videos/`. Один origin нужен для того,
  чтобы обойтись без CORS, а httpOnly-cookie авторизации (`samesite=lax`)
  без проблем работали из SPA.
- Frontend: Angular 22 (standalone, signals, zoneless), `frontend/`, пишет
  Claude по явной просьбе пользователя. Контракт API: ответы `GET /videos*`
  содержат `playback_url: string | null`.

**Шаги/находки:**
- `docker/nginx/nginx.conf` и сервис `nginx` в compose написаны Claude по
  просьбе пользователя. Конфиг монтируется как `conf.d/default.conf` (только
  блок `server`). Важные места: слэш в конце `proxy_pass` у `/api/` (срезает
  префикс), `client_max_body_size 10m` (дефолт 1 МБ < чанка 5 МБ),
  `proxy_read_timeout 600s` (синхронный `upload/complete` на больших файлах
  дольше 60с), `Host $host` + `Upgrade`/`Connection` для dev-сервера Angular.
- При первом запуске nginx: (1) `ng serve` слушал только IPv6 `[::1]`, а
  Docker Desktop ходит на `host.docker.internal` по IPv4 → 502; починено
  `"host": "127.0.0.1"` в `angular.json`. (2) Редирект `/api` → `/api/` уходил
  на `localhost:80` (внутренний порт контейнера); починено
  `absolute_redirect off`. Приложение открывается только через
  `http://localhost:8080`: на `:4200` `/api/*` отдаёт `index.html`.
- `backend/scripts/init_storage.py` (написан Claude по просьбе): идемпотентно
  создаёт бакет и вешает политику анонимного `s3:GetObject` на
  `videos/*/hls/*`. Проверено через nginx: HLS → 200, `original.mp4` и
  листинг → 403, `Range` на сегменте → 206.
- Найден и починен (с согласия пользователя) баг Этапа 4: `master.m3u8`
  ссылался на варианты как `1080p\playlist.m3u8`, потому что
  `_build_ffmpeg_command` передавал ffmpeg пути через `str(Path)`, а на Windows
  это обратные слэши. Исправлено на `.as_posix()`, тест
  `test_build_ffmpeg_command_has_variant_per_rendition` теперь требует прямые
  слэши. Видео, транскодированные до фикса (79, 80), не воспроизводятся.
- `playback_url` (написан Claude по просьбе): колонка `videos.hls_master_key`
  (nullable, миграция `b3f1c2d4e5a6_add_hls_master_key_to_videos`, написана
  вручную). `video_repository.mark_video_ready` ставит `READY` и ключ вместе
  (инвариант: `ready` ⇔ ключ заполнен), его вызывает `transcode_video` при
  успехе. Схема `VideoResponse` (`from_attributes`, `hls_master_key`
  исключён из JSON, `computed_field` `playback_url` = `settings.media_url_prefix`
  + ключ) подключена как `response_model` у get/list/chunk/complete. Тесты:
  в `test_transcode.py` проверяется ключ при успехе и `None` при всех трёх
  ошибках, в `test_video_crud.py` добавлены 3 теста на `playback_url`.
- Отложено: `delete_video` удаляет из MinIO только `original.mp4`. HLS
  удалённого видео остаётся в бакете и с новой политикой публично доступен.

## Как мы работаем вместе (правила для Claude)

- **Не писать код за пользователя**, если явно не попросил. Объяснять
  концепции, архитектуру, тыкать в проблемы в его коде, задавать наводящие
  вопросы. Дефолт — обсуждение и ревью, не реализация.
- Если пользователь просит написать код явно — это разовое исключение для
  конкретной задачи, не смена режима работы на постоянку.
- **Не выполнять команды (миграции, установка пакетов, `ruff --fix`, запуск
  тестов, git-операции и т.п.) без личной просьбы пользователя.** Даже когда
  задача явно требует такой команды (например, тесты не запустить без
  `pytest`) — сначала спросить или явно предложить и дождаться подтверждения,
  не делать по умолчанию "раз уж пишу тесты, заодно и прогоню". Исключение —
  команды, которые сам пользователь попросил выполнить в рамках задачи.
- При ревью — не просто "ок, работает", а объяснять **почему** так лучше
  или хуже, какие есть альтернативы, что будет проблемой в проде.
- Не забегать вперёд по этапам — если пользователь спрашивает про этап 4,
  пока не сделан этап 1, не стесняться напомнить про порядок и спросить,
  осознанно ли он перескакивает.
- Не считать, что пользователь уже знает то, что помечено как "не пройдено"
  в разделе "Мои вводные" — базовые вещи Python вроде декораторов, asyncio,
  pytest нужно объяснять с нуля при первой встрече в коде, а не предполагать
  знание.
- Технологии (Docker, Postgres, Redis, nginx, MinIO, Celery/RQ) — пользователь
  видит их впервые. Не считать очевидным ни один термин (образ vs контейнер,
  брокер vs воркер, миграция и т.д.) — объяснять при первом появлении.
- Обновлять чекбоксы и статус этапа в этом файле по ходу работы, когда
  пользователь подтверждает, что пункт сделан.
- Тесты к бизнес-логике этапа пишет Claude сам, как только логика готова и
  обсуждена — не дожидаясь отдельной просьбы каждый раз. Если по ходу
  тестирования всплывает баг в коде пользователя — не чинить его молча,
  явно указать на находку и согласовать фикс.
- По ходу разработки каждого этапа — как только сделан значимый шаг
  (реализована модель, роут, миграция, найден и исправлен баг, принято
  архитектурное решение) — фиксировать это в разделе этапа короткой записью:
  что сделано и почему, а не только финальным списком чекбоксов в конце.
  Это не журнал каждой мелкой правки, а трасса ключевых шагов, по которой
  потом можно восстановить, как и почему что-то получилось так, как есть.

Сквозной pet-проект: CineAgent

Один проект вместо двух разных — закрывает и backend-этап, и LLM-этап. Разговорный рекомендатель фильмов/сериалов: вместо фильтров — диалог ("хочу что-то как Breaking Bad, но покороче и повеселее"), агент вызывает инструменты поиска по своей БД и объясняет выбор, а не просто выдаёт список. Выбран сознательно вместо RAG-чата по субтитрам — ближе к тому, что реально называется «AI Engineer» в вакансиях (оркестрация инструментов, а не поиск по вектору), и меньше похож на типовой учебный проект.

Слои проекта и где какой навык из плана в него попадает:

  • Данные: каталог фильмов/сериалов через TMDB API (жанры, описание, длительность, актёры, рейтинги) → своя Postgres-схема
  • Семантика: эмбеддинги описаний в pgvector — поиск «по вайбу», не только по тегам жанра
  • Профиль: история просмотров/лайков пользователя — агент учитывает её без явного запроса
  • Инструменты агента: search_by_filters(), find_similar(title), get_user_history(), compare(title_a, title_b)
  • Объяснимость: structured output (JSON: кандидаты + reasoning) вместо голого текста — модель показывает, что учла и что отбросила
  • Frontend: чат + карточки рекомендаций, стриминг «мыслей вслух», индикатор во время tool call — прямое применение опыта со стриминговым UI

Этапы

Даты — не жёсткий контракт, а ориентир при 10–15 ч/нед. Если решите снизить нагрузку на frontend ближе к переезду — этапы 3–5 можно сжать почти вдвое (отмечено внутри).

2. Backend-минимум

22.09 – 30.11.2026 (~10 нед)

Цель — не Senior Backend, а «уметь поднять API + БД + авторизацию под свой проект». Жёсткий тайм-бокс: 10 недель, дальше — переход к LLM, даже если что-то не идеально. Здесь строится backend-фундамент CineAgent — пока без LLM, просто рабочий каталог с API.

  • HTTP/REST с нуля: методы, статус-коды, заголовки, JSON-контракты
  • FastAPI (не Flask/Django — ближе к тому, что используют в AI-стеке): роуты, Pydantic-модели, dependency injection
  • БД: PostgreSQL — SQL-минимум (SELECT/JOIN/INSERT), затем SQLAlchemy/ORM; схема фильмов/жанров/пользователей для CineAgent
  • Интеграция с TMDB API: загрузка каталога фильмов/сериалов (метаданные, жанры, описания, рейтинги) в свою БД
  • Авторизация: JWT, хеширование паролей (bcrypt) — свой профиль пользователя с историей просмотров/лайков
  • Docker-минимум: Dockerfile, docker-compose для локального Postgres + приложения
  • Деплой CineAgent API (без LLM-части) на Railway/Render/Fly.io — аналог понятен из фронтенд-опыта (Vercel/Netlify)
📦 Итог этапа: CineAgent v0 — CRUD API поверх каталога TMDB с авторизацией и историей пользователя, задеплоенный, репозиторий открыт.
⚠️ Главный риск плана: здесь легче всего застрять в «ещё немного доучу бекенд». Держите тайм-бокс — деплой хуже, но вовремя, лучше идеального, но бесконечного.

3. LLM API — первое знакомство

13.10 – 30.11.2026 (внахлёст с этапом 2)

Начинается на середине backend-этапа, не после. Это просто HTTP-запросы — ждать «полной готовности» не нужно. Первые эксперименты — уже на данных CineAgent.

  • Anthropic/OpenAI API: обычные запросы, стриминг, system-промпты
  • Токены, контекстное окно, ценообразование — как это влияет на архитектуру продукта
  • Tool calling / function calling — базовый паттерн агентности
  • Промпт-инжиниринг: few-shot, структурированный вывод (JSON mode)
  • Пробный скрипт: LLM описывает/резюмирует карточку фильма из своей БД CineAgent
📦 Итог этапа: CLI-скрипт на Python, который дергает LLM API и обрабатывает данные из БД CineAgent.
Ключевой этап

4. LLM-интеграция в продукт

01.12.2026 – 15.02.2027 (~11 нед)

Здесь собирается ваше отличие от «чистого» backend или ML-инженера: продукт целиком — от UI до вызова модели. CineAgent v0 превращается в полноценного разговорного агента-рекомендателя.

  • Векторный поиск: эмбеддинги описаний фильмов в pgvector — поиск «по вайбу», не только по тегам жанра (find_similar(title))
  • Инструменты агента: search_by_filters(), find_similar(), get_user_history(), compare(a, b) поверх CRUD API из этапа 2
  • Оркестрация: голый API без фреймворка на старте (осознанный выбор — фреймворки часто лишние), LangChain/LlamaIndex — опционально позже
  • Агенты: ReAct-паттерн, multi-step tool use, память диалога + история пользователя как контекст
  • Объяснимость: structured output (JSON: кандидаты + reasoning) — агент показывает, что учёл и что отбросил, не просто выдаёт список
  • Стриминг в UI: SSE/WebSocket, «мысли вслух» и индикатор во время tool call — здесь ваш frontend-опыт даёт фору
  • Гардрейлы: обработка ошибок модели, rate limits, fallback-и, оценка стоимости запроса
📦 Итог этапа: CineAgent v1 — разговорный рекомендатель с tool calling, семантическим поиском и объяснением выбора, задеплоен.

Честная критика плана

План здоровый и небезосновательный — но вот что в нём стоит держать под подозрением.

Три больших трансформации одновременно — это перегрузка, а не план "по очереди"

Python → backend → LLM → переезд → английский B2 → смена профессии выглядят как последовательность, но по факту с этапа 3 они все идут параллельно. 10–15 ч/нед — это ~1.5–2 ч в будний день. На таком бюджете одновременно учить FastAPI/SQL, LLM-паттерны и подтягивать английский с A2 до B2 — реально, но без запаса на непредвиденное (аврал на основной работе, болезнь, спад мотивации).

Что делать: относиться к датам как к коридору ±3-4 недели, а не дедлайну. Если что-то одно начинает страдать — жертвовать глубиной backend-этапа, не английским и не практикой с LLM (это явно сформулированный приоритет в исходном плане).

English A2 → B2 за 8–11 месяцев на самостоятельном режиме — оптимистичная оценка

По ориентирам CEFR один уровень (A2→B1 или B1→B2) — это обычно 200+ учебных часов при регулярных занятиях с преподавателем. Два уровня за год при 10–15 ч/нед, из которых английский — лишь часть, реалистичнее закрывают на твёрдый B1, а не B2.

Что делать: закладывать B1+ как реалистичную цель к моменту переезда, а B2 — как цель уже в Сербии, где есть языковая среда и время (жизнь на сбережения год без работы — это ресурс, которым стоит явно воспользоваться для интенсива в первые месяцы там).

Этап 2 (backend) — единственный этап без встроенного продукта, риск "учу ради знаний"

В отличие от этапов 3-5, где каждый шаг заканчивается артефактом, backend-этап по формулировке "изучить основы" — самый расплывчатый и самый вероятный кандидат на разрастание, что признано и в исходном конспекте как главный риск.

Что делать: план уже фиксирует тайм-бокс 10 недель — держитесь его буквально, включая деплой. Если к концу 10-й недели авторизация "почти работает" — деплойте как есть и чините в процессе этапа 4, а не откладывайте переход.

"Занятость не определена" — решение откладывается, а оно определяет всё остальное

Разница между full-time и part-time/увольнением перед переездом — это разница между планом на 12 месяцев и планом на 5-6. Пока решение не принято, план держит self-consistent сценарий "full-time весь период", что по умолчанию консервативно — не переоценивайте скорость, если сохраните полную нагрузку.

Что делать: зафиксировать решение не позже конца этапа 2 (~ноябрь 2026) — к этому моменту будет понятно, устраивает ли темп, и есть ли смысл снижать нагрузку на frontend ради ускорения LLM-этапов перед переездом.

Портфолио из 3 похожих чат-ботов не сработает так, как из 3 разных задач

Риск: RAG-чат по PDF — самый частый учебный проект в этой нише. CineAgent снижает этот риск (tool calling/агентность встречается реже, чем голый RAG), но третий проект всё равно должен закрывать другую способность LLM, а не быть вторым рекомендателем.

Что делать: третий проект уже сознательно выбран другим форматом (этап 5) — но также ценно довести именно CineAgent до состояния "показать вживую на созвоне" с реальным диалогом, а не просто ссылку на GitHub.

CineAgent зависит от внешнего API (TMDB) — точка отказа вне вашего контроля

Rate limits, изменения схемы ответа или условий использования TMDB могут сломать демо в неподходящий момент (например, прямо на собеседовании). Отдельно: TMDB данные нельзя выдавать за собственную БД без указания источника — это не критично для pet-проекта, но стоит явно упомянуть атрибуцию в README.

Что делать: на этапе 2 сразу сохранять снэпшот каталога в свою БД (не проксировать TMDB "вживую" при каждом запросе) — тогда демо не зависит от доступности стороннего сервиса в момент показа.

Что в плане сильно: тайминг рынка и использование существующего актива

LLM-интеграция как инфраструктурный сдвиг на 5-10 лет — обоснованная ставка, не хайп-погоня. Стратегия "остаться frontend-специалистом + добавить слой LLM" вместо смены на 3-4 профессии — сильно снижает риск неудачи по сравнению с попыткой стать ML Researcher или чистым backend-инженером с нуля.

Год жизни в Сербии на сбережениях без необходимости работать — редкий ресурс: это время можно использовать не только на язык, но и на дожатие 2-3 проекта и активный нетворкинг без давления "нужна зарплата уже сейчас".

Как обновлять этот план: прогресс по Python уже трекается в CLAUDE.md проекта (журнал уроков + чек-лист). Этот документ — более крупная карта поверх него: имеет смысл сверяться раз в 2-4 недели и сдвигать даты по факту, а не подгонять факт под даты.
